# Garden-Spirit 前端 IA / UIUX V8

> V8 目标：把 Garden-Spirit 从“多个功能入口”升级为“用户每天可以回来的疗愈陪伴空间”。本规划不是单纯 UI 改版，而是同时收口五页职责、Chat 产品闭环、信箱记忆资产、宇宙主题观星台、报告商业化分层，以及“体系一 / 体系二 / 迁移”的前端表达规则。

---

## 1. 产品总定位

Garden-Spirit 不是占星 Dashboard，也不是普通 AI 聊天工具。

它的核心体验应该是：

```text
我今天回来了。
星灵在。
花园记得我。
我可以聊，可以被看见，也可以把重要的东西留下来。
```

V8 的关键词：

- **疗愈空间**：首页首先是一个能安静回来的花园，而不是信息面板。
- **陪伴闭环**：Chat 不能只停留在回复，要让用户看到点亮、记忆、来信、验证和报告资产如何发生。
- **记忆资产**：信箱不是消息列表，而是“花园记得我”的地方。
- **内在地图**：宇宙页承接自我星盘轮、主题观星台、证据链与沉淀判断。
- **账号关系**：我的页承接常驻星灵、权益、隐私、设置，不再抢预测入口。
- **规则统一**：体系一 / 体系二 / 迁移必须进入前端规划，不能让旧命名和旧入口造成感知混乱。

## 2. 五页职责边界

| 页面 | 一句话职责 | 核心体验 | 不做什么 |
|---|---|---|---|
| 首页 / 花园 | 今天谁来陪我 | 打开一个安静空间，星灵在等我 | 不做 Dashboard，不堆报告和预测入口 |
| Chat | 陪伴过程与闭环 | 聊完知道发生了什么：点亮、记忆、来信、验证 | 不做一次性问答工具，不削弱免费体验 |
| 信箱 | 记忆资产 | 今日来信、记忆来信、手账、推导链 | 不做普通消息流，不把脚注和正文混在一起 |
| 宇宙 | 内在地图枢纽 | 自我星盘轮 + 主题观星台 + 证据沉淀 | 不做报告商品货架，不伪造预测 |
| 我的 | 账号 / 权益 / 关系设置 | 常驻星灵、VIP、邀请、隐私、安全 | 不做预测入口，不和宇宙重复 |

## 3. 前端硬线

这些规则必须贯穿 V8 后续所有页面开发：

- 占星结论只来自 Domain / Conclusion / Finding / Report API。
- LLM 只负责疗愈表达、转述、追问，不负责结论合成。
- 前端不能硬编码年运、月运、婚运、桃花、人生走向、事业、财富等预测结论。
- 没有 API 或 Report Compiler 支撑的主题，只能显示“将接入星图证据链 / 暂未开放”。
- 免费 Chat 不能为了卖报告而故意变弱。
- 报告卖的是结构化资产价值：章节、保存、证据链、时间线、复盘、继续深聊上下文。
- 不恢复第二套 `house_nature` 路由。
- 不把 `TimelineWindow.net_score` 包装成用户可见的“净吉凶分”。
- 前端只消费后端确定性占星结果；不能让 LLM 或前端判断承诺、征象星、吉凶、权重和时机权威。

## 4. 占星判断链路清账

V8 后续所有年运、月运、人生走向、主题报告和主题观星台能力，都必须先服从同一条后端确定性判断链。当前项目的占星层已经出现多套 `score`、多种技法权威、多个输出对象混用的问题，因此 V8 必须把这条链路写进规划，作为前端、LLM、Report Compiler 和后端 Domain 的共同边界。

### 4.1 总原则

- **本命盘是地基**：先判断一个主题在命盘里有没有承诺、承载者是谁、强弱与阻力在哪里。
- **法达是人生章节主轴**：法达大限 / 子限定“这一阶段的主旋律”，继续作为人生阶段与长期时机的主权威。
- **年度小限是辅助层**：小限可以回归，但只能作为 `annual_activation`，回答“这一岁哪一宫被点亮、年主星是谁”，不能抢法达权威。
- **行运只做触发**：行运不能单独断事，必须打到本命承载者、法达主星、小限年主星或角点，才进入有效证据链。
- **人生经历用于校准**：已发生且被用户确认的事件进入后端证据层，用来校准同一星象在这个人身上通常如何兑现。
- **LLM 只转述和追问**：LLM 可以疗愈表达、总结、追问验证，不能自行改占星判断。
- **前端只展示契约字段**：前端只能消费 Domain / Conclusion / Finding / Report API，不计算、不拼装、不硬编码预测结论。

### 4.2 唯一主链路

```text
Chart
→ 本命承诺
→ 动态承载者
→ assess_planet 三轴评估
→ helper / ally / reception chain
→ 主题 resolver
→ 时间层：Firdaria 主轴 + annual_activation 辅助 + transit trigger
→ 人生事件校准
→ EvidenceChain
→ Conclusion / Finding / Report
→ LLM 转述 / 前端展示
```

每一层只回答自己该回答的问题：

| 层级 | 职责 | 不做什么 |
|---|---|---|
| 基础盘数据 | 行星、宫位、相位、尊贵、接纳等事实 | 不下吉凶结论 |
| 本命承诺 | 判断主题是否有命盘承诺、该看哪些宫与星 | 不直接预测年份 |
| 承载者 | 动态确定宫主星、自然征象星、角点、劫夺与穿刺 | 不固定“某主题永远只看某星” |
| 状态评估 | `assess_planet` 输出本质 / 境遇 / 关系三轴正负分开 | 不合成用户可见净分 |
| 连接链 | 判断互溶、接纳、帮手、压力、相位连接 | 不把单一相位独立断事 |
| 主题 resolver | 事业、关系、财富、学习、家庭、内在疗愈等专项判断 | 不绕过通用证据链 |
| 时间层 | 法达定章节，小限定年度点亮，行运定触发 | 不让小限或行运抢主权威 |
| 事件校准 | 用用户确认经历校准兑现方式和敏感触发 | 不让 LLM 自行改判断 |
| 输出契约 | 生成 EvidenceChain / Conclusion / Finding / Report | 不输出散文替代结构化证据 |

### 4.3 分数与证据边界

V8 禁止继续把所有 `score` 当成同一种占星强弱分。每类分数必须有明确业务语义：

| 分数线 | 字段示例 | 用途 | 用户可见规则 |
|---|---|---|---|
| 尊贵状态线 | `DignityState`、`dignity_score` | 入庙、曜升、三分、在界、在面、落陷、失势 | 标签必须来自状态；`dignity_score` 仅兼容 / 审计，不作权威标签 |
| 行星评估线 | `essential_pos/neg`、`accidental_pos/neg`、`relational_pos/neg` | 三轴吉凶两论，Domain 判断权威来源 | 可转成“有支撑 / 有压力”证据，不显示净分 |
| Evidence 权重线 | `payload.score`、`weight`、`raw_score` | 证据强弱、排序、审计 | `raw_score` 只审计；用户看证据，不看原始分 |
| 时间窗口线 | `TimelineWindow.net_score`、TimingStack `score/tag` | 窗口排序、强度、机会 / 压力分轨 | 不包装成“净吉凶分” |
| 置信度线 | `confidence`、`trust_score` | 判断被验证程度、关系信任 | 可显示“把握 / 待验证”，不等于吉凶 |
| 成长线 | `fragment.depth`、`level`、`action_count` | 陪伴成长、碎片点亮、行动复利 | 不做人格评分 |
| 推荐线 | spirit recommendation `score` | 星灵推荐排序 | 不等于行星强弱或好运坏运 |

### 4.4 技法权威顺序

后续新增或恢复技法必须按以下权威顺序组合：

1. **本命盘**：有没有承诺、主题落在哪里、谁是承载者。
2. **`assess_planet`**：承载者强在哪里、受限在哪里、谁在帮、谁在压。
3. **法达**：当前人生章节和阶段主旋律。
4. **年度小限 `annual_activation`**：这一岁哪一宫被点亮、年主星是谁，只作为年度辅助。
5. **行运触发**：什么时候敲钟，必须命中本命承载者 / 法达主星 / 小限年主星 / 角点。
6. **已验证事件**：这个人过去如何兑现类似结构，用来校准表达方式。
7. **Conclusion / Report**：统一输出判断、证据、时间窗口、建议和待验证点。

禁止回潮：

- 不让年度小限和法达并列抢权威。
- 不让行运单独断婚姻、事业、财富或重大事件。
- 不让 `planet_strength`、`dignity_score`、`raw_score` 重新成为新业务的判断入口。
- 不把三分 / 在界 / 在面改写成“入旺”或“大旺”。
- 不把机会 / 压力双轨净值化成用户可见“好运坏运分”。

### 4.5 分阶段占星能力路线

1. **阶段一：收口 v3 地基**
   - 稳定 `assess_planet`、动态承载者、R10 guardrail、法达 Timing、helper / ally chain。
   - 给前端明确后端契约：哪些字段是确定性占星事实，哪些只是疗愈转述素材。
   - 目标：后端输出证据链，不输出散文替代判断。

2. **阶段二：年度小限作为辅助层回归**
   - 新增 / 恢复 `AnnualProfection`，但出口命名为 `annual_activation`，不是 `timing_authority`。
   - 输出年龄、年度宫位、年主星、年主星状态、与本命主题的关系。
   - 与法达组合为：法达主章节 + 小限年度宫位 + 行运触发对象。
   - 防止旧逻辑回潮：年主星不能直接断婚姻 / 事业 / 财富。

3. **阶段三：Life Rhythm 人生阶段模型**
   - 建立 `LifeRhythm / LifeStage / LifeChapter` 后端模型。
   - 每段人生阶段包含年龄范围 / 日期范围、法达大限 / 子限、被点亮主题、关键承载者、opportunity / pressure 双轨、已验证人生经历、未来可能表达方式。
   - 目标输出不是“好运坏运”，而是“人生节奏”：什么时候重事业，什么时候重关系，什么时候重内在重建。

4. **阶段四：人生经历校准**
   - 新增关键人生事件结构：年份、领域、事件类型、用户确认程度、关联证据。
   - Domain 用事件校准：哪些宫主星已经被验证、哪类行运更敏感、某颗星在用户生命里偏事业 / 关系 / 家庭 / 心理层表达。
   - LLM 只能询问和总结，不能自行改占星判断。

5. **阶段五：主题专项判定**
   - 事业方向：10 宫、6 宫、2 宫、MC、太阳 / 土星 / 火星 / 木星。
   - 关系婚姻：7 宫、5 宫、8 宫、金星 / 火星 / 月亮 / 太阳 / 土星，后补性别征象星链。
   - 财富结构：2 宫、8 宫、11 宫、木星 / 金星 / 水星，区分正财、副业、他人资源。
   - 内在疗愈：4 宫、8 宫、12 宫、月亮 / 土星 / 海王，贴合产品疗愈定位。

6. **阶段六：预测报告技法增强**
   - 年度报告：法达 + 年度小限 + 太阳返照 + 重点行运。
   - 月度报告：法达子限背景 + 月亮返照 + 行运触发。
   - 人生报告：法达全周期 + 小限年度节奏 + 已验证事件校准。
   - 后置技法：次限月亮、太阳弧、黄道释放、orb、速度、福点 / 月相、命主星特殊权重。

### 4.6 评测与护栏

- 每个技法必须有测试，不能只写文档。
- 每个结论必须有 evidence chain：宫位、承载者、状态、连接、时间层。
- 禁止用户可见“净分 / 净吉凶”。
- 禁止 LLM 决定吉凶、权重、征象星、时机权威。
- 禁止前端硬编码占星判断。
- 禁止年度小限和法达并列抢权威。
- 火星双子在界、三分 / 在界 / 在面等小尊贵必须显示为有限支撑，不能被标签或转述升级为入旺。

## 5. 体系一 / 体系二 / 迁移融合

这部分是 V8 核心，不是后端附录。

### 5.1 为什么必须写进前端规划

用户对产品能力的理解首先来自页面入口和文案。如果前端仍然保留多套旧命名、多套旧入口、多套“看法”，即使后端已经统一，用户仍会觉得系统互相覆盖、规则混乱。

所以 V8 要把后端迁移后的新秩序展示出来。

### 5.2 当前权威口径

- **体系一**：`ConsultResolver` keyword 路由是资产，不删除。它升级为“语义场词典 + 正则 + LLM 兜底”的入口资产。
- **体系二**：旧 `house_nature` 路由不恢复为第二套系统；它的职责已经合并进 `house_significations` / `house_derived`。
- **最终入口形态**：从写死 `TopicPlan` 升级为 `{ domain, focus_house, focus_slice, 承载者 }`。
- **领域模块**：Career / Wealth / Risk 等专用模块是“领域放大器”，不覆盖通用语义场。
- **迁移路线**：合一词汇 → 补语义场 → 领域定义数据化 → 合成器 + 模块转型。

### 5.3 前端如何表达迁移结果

| 场景 | V8 表达 |
|---|---|
| 用户入口 | 使用“主题观星台”，不再强调“星盘咨询” |
| 自我地图 | 使用“自我星盘轮”，承接 3 大类 / 34 子类闭环 |
| 主题卡 | 显示主题、适合问什么、开放状态、证据链状态 |
| 沉淀判断 | 显示后端给出的待验证 / 已确认状态 |
| 证据链 | 显示宫位、语义切片、承载者等后端字段，不前端推断 |
| 报告 | 显示报告章节和资产状态，不在前端生成占星解释 |

### 5.4 禁止回潮

- 不恢复 `house_nature` 成为第二套路由。
- 不在前端新增“某主题固定看某宫某星”的硬编码。
- 不让主题观星台绕开 Domain 输出。
- 不把旧“星盘咨询”继续作为用户主命名；内部 `consult.vue` 路由可暂保留，用户文案迁移。

## 5. 首页：今日花园场景

首页只回答一个问题：**今天，谁来陪我？**

### 5.1 当前问题

当前首页主要问题不是信息少，而是：

- 视觉像“黄绿底色 + 中间星灵 + 点击说话 + 底部 tab”。
- 背景层级互相打架，没有形成一个完整场景。
- 星灵像孤立头像，不像在花园里等用户。
- 入口虽少，但缺少“花园记得我”的陪伴感。
- 用户不知道今天为什么是这颗星灵、可以从哪里开始。

### 5.2 V8 视觉方向

统一为一个“今日花园场景”，不要两层背景互相打架。

| 时间 | 视觉关键词 |
|---|---|
| 晨间 | 浅雾、柔光、露水、淡金绿 |
| 午后 | 温暖光斑、植物阴影、奶油绿 |
| 黄昏 | 橘金、萤火、慢雾、粉紫边缘 |
| 夜晚 | 深绿夜空、星点、月光、安静光晕 |

### 5.3 星灵形象方向

星灵不是孤零零站在中间，而是“坐在花园里等你”。

- 有身体感、手脚暗示、坐姿或等待姿态。
- 有光环、植物、碎片星光、轻微漂浮元素。
- 不同星灵可使用同一基础体型，通过衣服、颜色、纹样、道具区分。
- 当前阶段继续复用 `SpiritPortrait`，后续资产到位再升级 embodied companion。

### 5.4 首页结构

1. 日期 / 今日光线。
2. 星灵主视觉。
3. 一句陪伴话，不是功能说明。
4. 今日陪伴卡：
   - 今日陪你的星灵。
   - 为什么是它。
   - 它今天想陪你看什么。
5. mood check：
   - 疲惫。
   - 想被理解。
   - 有点乱。
   - 想知道答案。
6. 轻入口：
   - 和它聊聊。
   - 继续昨天。
   - 今日来信。
   - 今日被照见的碎片。
   - 待验证提醒。

首页不要出现完整报告列表、复杂数据面板或预测货架。

### 5.5 插画 Prompt 方向

可用于生成首页背景插画：

```text

```

夜间版本：

```text
A quiet night garden sanctuary for a spiritual companion app, deep emerald green night sky, soft moonlight, tiny stars, glowing fireflies, mist around leaves and flowers, magical companion sitting peacefully in the garden, healing and intimate atmosphere, elegant painterly illustration, premium emotional wellness design, no text, mobile vertical composition, soft glow, calming and safe
```

星灵角色方向：

```text
A small embodied spirit companion character, soft rounded body, visible tiny hands and feet, sitting gently as if waiting for the user, wearing planet-inspired clothing and accessories, warm expressive eyes, healing and calm, premium companion app mascot, not cartoonish, not childish, soft fabric texture, subtle celestial motifs, full body, transparent background
```

## 6. Chat：产品闭环打通

Chat 是陪伴过程，不是一次性问答页。

### 6.1 当前问题

当前 Chat 已有后端富反馈字段，但前端主要表现为临时提示文案，用户不能稳定感知“聊完之后发生了什么”。

需要把这些字段做成可见闭环：

| 字段 | UI 表达 |
|---|---|
| `lit_fragments` | 点亮了哪些内在角落 |
| `seen_fragments` | 哪些确认被星灵记住 |
| `actioned_fragments` | 哪些行动进入成长账本 |
| `keepsake_created` | 新的记忆来信已放进信箱 |

### 6.2 V8 闭环卡

当一次回复产生沉淀时，助手气泡下方出现轻量闭环卡：

- “点亮了 2 个内在角落”。
- “这次确认，星灵记住了”。
- “一封新的记忆来信已放进信箱”。
- 操作入口：
  - 去信箱。
  - 看碎片。
  - 继续追问。
  - 整理成报告。

“整理成报告”当前只作为未来入口或 toast，不生成伪报告。

### 6.3 Chat 与报告的边界

- Chat = 陪伴、信任、即时探索、点亮、记忆写回。
- Report = 结构化资产、可保存、可复盘、证据链、时间线、多章节。
- 用户拿报告继续 Chat 时，Chat 应围绕该报告上下文深聊，而不是前端重新生成一份报告。

## 7. 信箱：记忆资产空间

信箱核心感受：**花园记得我。**

信箱不是普通消息流，也不是把所有信件正文直接摊开。V8 信箱要成为一个“每日提醒 + 记忆资产 + 手账沉淀”的空间：用户先看到今日有什么，再进入具体信件详情。

### 7.1 当前问题

信箱已经有今日来信、keepsake、手账、碎片脚注、星图线索和推导链，但当前体验存在明显断点：

- 顶部几个标签视觉上像可点击筛选，但点击后没有真实作用。
- 信箱内容没有分类，daily / keepsake / journal / fragment footnote 混在一起。
- 今日来信正文直接铺在页面里，用户缺少“列表 → 详情”的收信动作。
- 来信脚注、碎片、落款推导链和正文混在同一层，记忆资产感被稀释。
- 每日日推目前更像“单条今日来信”，没有承接 0:00–24:00 的整日提醒列表。

### 7.2 V8 信息层级

1. **当日日推**：每日 0 点按盘主本地日重置，一次性生成当天 0:00–24:00 的全部提醒。
2. **来信列表**：daily / keepsake / journal 统一作为信件资产列表展示。
3. **来信详情**：点击列表项进入正文、脚注、星图线索、推导链。
4. **今日灵魂碎片**：作为脚注数据卡，不混进正文。
5. **星图线索**：今日光线 / 记忆镜头 / 行运触发 / 宫位场景。
6. **落款推导链**：为什么是这颗星灵写下这封信，默认折叠。

### 7.3 当日日推格式

日推定义：**每日 0 点，以用户本地日为单位，生成当天 0:00–24:00 的行运生活提醒；有几条推几条，统一组成“当日日推”。**

日推不是事件预言，而是当天生活场景提醒。一次推送/一次生成内可以包含多条：

```text
今日星灵日推 · 8月18日

今天共有 3 个时间窗口值得慢一点：

1. 上午｜通勤 / 开车 / 消息文书
   月亮会触发你3宫里的木星，短途、开车、路口、导航和消息文书更容易被点亮。
   同一木星也被天王、海王托起，临时变化和判断模糊感需要多留一眼。

2. 全天偏强｜身体劳损 / 日常工作
   火星正在引动你的6宫主，久坐起身、腰背用力、赶时间硬扛都要放慢。

3. 全天背景｜保险 / 赔付 / 责任记录
   土星触发8宫场景，涉及保险、赔付、责任认定和共同钱，证据和记录留清楚。

不是说一定会发生什么，只是这些生活场景今天更容易被点亮。
```

#### 7.3.1 日推卡片字段

| 字段 | UI 文案 | 说明 |
|---|---|---|
| `letter_date` | 8月18日 | 盘主本地日期 |
| `summary` | 今天共有 3 个时间窗口值得慢一点 | 整日日推摘要 |
| `items[]` | 日推条目 | 有几条展示几条，不固定数量 |
| `time_label` | 上午 / 下午 / 全天背景 | 生活化时间窗口，不吓人 |
| `scene` | 通勤 / 开车 / 消息文书 | 生活场景优先于术语 |
| `sender` | 月亮 / 火星 / 土星 | 可显示星灵头像或小徽标 |
| `level` | L1–L3 | 内部强度可轻展示，不做吉凶分 |
| `body` | 一句话提醒 | 面向用户的温柔提醒 |
| `reason_chain` | 行运月亮刑本命3宫木星... | 详情页折叠展示 |
| `disclaimer` | 不是说一定会发生什么... | 每日日推固定底线文案 |

#### 7.3.2 日推列表项样式

日推条目在列表里像一张“今日便签”，不是报告表格：

```text
┌────────────────────────────┐
│ 上午        月亮 · 3宫       │
│ 通勤 / 开车 / 消息文书       │
│ 路口、车距、导航多留一眼。   │
│ 2 条星图线索  ›             │
└────────────────────────────┘
```

视觉规则：

- 时间窗口放左上，星灵 / 宫位放右上。
- 生活场景作为主标题，术语退到详情页。
- L2/L3 条目可加淡金描边；不使用红色警报感。
- 同一日多条提醒按 `time_label` 与强度排序：清晨 → 上午 → 中午 → 下午 → 傍晚 → 夜间 → 全天背景。

### 7.4 信箱首页结构

信箱页默认显示“列表”，不直接铺正文。

1. 顶部标题区：
   - `信箱`
   - 副文案：`花园替你收着这些被看见的时刻`
2. 今日摘要卡：
   - 今日是否有日推。
   - 今日未读数量。
   - 今日被点亮碎片数。
   - CTA：`查看今日日推`。
3. 分类标签：
   - `全部`
   - `当日日推`
   - `记忆来信`
   - `我的手账`
   - `星图线索`
4. 信件列表：
   - 按时间倒序。
   - 每项只显示标题、摘要、类型、发件星灵、日期、未读状态。
5. 空状态：
   - 不显示空白列表。
   - 文案：`花园还在等第一封信。和星灵聊聊，重要的时刻会被放进这里。`
   - CTA：`去花园聊聊`。

### 7.5 分类标签必须真实可用

当前几个标签如果保留，就必须有筛选效果；否则不要做成可点击标签。

| 标签 | 包含内容 | 空状态文案 |
|---|---|---|
| 全部 | daily + keepsake + journal | 暂时还没有信件 |
| 当日日推 | 每日 0:00–24:00 日推集合 | 今天还没有生成日推 |
| 记忆来信 | Chat 产生的 keepsake | 还没有被收藏成来信的时刻 |
| 我的手账 | 用户主动写下的 journal | 还没有写下手账 |
| 星图线索 | 有 reason_chain / fragment footnote 的信件 | 还没有可展开的星图线索 |

交互规则：

- 点击标签只筛选列表，不跳页。
- 标签选中态使用浅金底 + 深绿字；未选中为半透明纸片。
- 标签下方显示当前分类数量，例如 `记忆来信 12`。
- 如果某分类为空，展示该分类专属空状态和一个行动按钮。

### 7.6 来信列表项

列表项要让用户愿意点进去，而不是一次读完。

每个列表项包含：

- 类型徽标：`日推` / `记忆` / `手账` / `线索`。
- 标题：如 `火星提醒`、`「想被抱抱的我」来信`。
- 摘要：正文前 1–2 行，不展示脚注。
- 元信息：星灵、日期、是否未读、有无碎片、有无推导链。
- 右侧箭头：进入详情。

示例：

```text
┌────────────────────────────┐
│ 日推 · 未读        火星 ✦   │
│ 8月18日的今日星灵日推       │
│ 今天共有3个时间窗口值得慢一点│
│ 3条提醒 · 4条星图线索   ›   │
└────────────────────────────┘
```

```text
┌────────────────────────────┐
│ 记忆来信          月亮 ✦   │
│ 「想被抱抱的我」来信        │
│ 你刚才说的那件事，被花园轻轻收好了… │
│ 2个灵魂碎片 · 推导链     ›  │
└────────────────────────────┘
```

### 7.7 来信详情页

点击列表项进入详情页。详情页是完整信纸，不再混在列表中。

详情结构：

1. 顶部返回：`‹ 信箱`。
2. 信件头部：
   - 类型徽标。
   - 标题。
   - 发件星灵头像 / 名称。
   - 日期和时间窗口。
3. 正文信纸：
   - 半透明奶白纸页。
   - 行高放松。
   - 落款右下角。
4. 当日日推条目区（仅 daily）：
   - 展示当天所有 `items[]`。
   - 每条可展开星图线索。
5. 今日灵魂碎片脚注：
   - 作为独立小卡。
   - 点击可去宇宙碎片详情。
6. 星图线索：
   - 默认折叠。
   - 展开后显示宫位、行星、相位、reason_chain。
7. 落款推导链：
   - keepsake 默认折叠展示。
   - 日推可展示“为什么今天是这几颗星灵”。

详情页底部操作：

- `和它继续聊聊`
- `查看相关碎片`
- `整理成手账`（未来入口，不伪造报告）

### 7.8 视觉方向

- 整体是“信箱小屋 / 纸页抽屉”，不是系统消息中心。
- 背景延续花园时间光线，但比首页更安静，使用奶白、浅绿、淡金。
- 列表卡片像叠放信笺：圆角 24、轻阴影、半透明纸感。
- 未读信件左侧有一颗小金点，不使用强红点。
- 分类标签像贴在信盒上的小纸签。
- 详情正文是完整信纸，脚注和推导链是纸页下方的星尘便签。
- 星图线索用细线连接：`行运触发 → 本命承载点 → 生活场景 → 建议`。

### 7.9 红点规则

- 信箱底部导航红点 = 今日来信 / 当日日推未读。
- 进入信箱列表后本地先 `markLetterBadgeRead()`，再 fire-and-forget `markLettersReadToday()`。
- 如果用户只进入列表但未点详情，列表内该信仍可保留“未读金点”；底部总红点可消除。
- 红点共享状态使用 `gardenBadges.ts`，不要每页各算各的。

## 8. 宇宙：内在地图枢纽

宇宙页不是报告列表，而是“我这张内在地图在哪里发光”。

### 8.1 当前问题

宇宙页星空背景方向可以保留，但内容层级混在一起：自我星盘轮、星盘咨询、未来预测、沉淀判断没有清楚分层。

### 8.2 V8 三层结构

1. **自我星盘轮**
   - 3 大类 / 34 子类。
   - 当前最完整的闭环功能。
   - 用户补齐 icon 资产后继续接入现有 fallback 链。

2. **主题观星台**
   - 替代“星盘咨询”的前端命名。
   - 承接未来主题和报告。
   - 当前只展示入口与证据链契约，不伪造预测结论。

3. **沉淀判断 / 证据链**
   - 待验证判断。
   - 已确认结论。
   - 可追问证据。
   - 后端输出什么，前端展示什么。

### 8.3 主题观星台分类

| 大类 | 说明 |
|---|---|
| 年运 | 年度主题、关键月份、机会/压力窗口 |
| 月运 | 本月情绪、行动节律、提醒 |
| 人生走向 | 长周期阶段、法达章节、人生规划 |
| 情感 | 恋爱、关系模式、伴侣议题 |
| 事业 | 职业路径、表达、机会、风险 |
| 财富 | 正财、偏财、资源流动 |
| 学业 | 学习方式、考学、深造 |
| 自我 | 性格、灵魂课题、自我理解 |
| 家庭 / 亲子 | 原生家庭、父母、亲子关系 |

### 8.4 主题观星台 → 报告型意图契约

主题观星台后续不再只靠一段 Chat seed text 进入咨询，而是向 Chat / Report Compiler 传递结构化入口上下文。这个上下文只帮助后端理解“用户从哪里来、原始问题是什么、是否可能跨主题”，不生成任何占星结论。

核心边界：

- `entry_topic_key` / `topic_key` 是入口上下文，不是 hard lock；用户从事业入口进入，也可以真实询问家庭、母亲、关系对事业的影响。
- `primary_topic` 是意图层和 Domain 共同收敛后的主问题；`secondary_topics` 是跨主题影响来源。
- `intent_shape` 至少支持：`single_topic`、`cross_topic_influence`、`topic_switch_suggested`、`clarification_required`、`unsupported`。
- `report_type` 只表示产品形态：`monthly`、`annual`、`life_rhythm`、`theme`；它不是占星技法本身。
- `user_focus_text` 必须保留用户原始问题，不能被前端改写成模板结论。

推荐契约：

```text
entry_source = observatory
entry_topic_key = career
primary_topic = career
secondary_topics = [family]
intent_shape = cross_topic_influence
report_type = theme
user_focus_text = 我想看和母亲的关系对我事业的影响
```

后端处理原则：

- Domain 不维护无限用户语言切片；Domain 维护有限、可组合、可审计的 astrology semantic atoms。
- LLM 可以把开放语言翻译成候选需求，但必须交给 Domain canonicalize / accept / reject / clarify。
- 跨 topic 问题是一等场景，不能强行塞回入口主题模板。
- 主题观星台只能传入口上下文、开放状态和证据链状态；不能前端判断宫位、行星、征象星、吉凶、权重或时机权威。

示例：

```text
用户从 career 卡进入：
user_focus_text = 我想看和母亲的关系对我事业的影响

正确理解：
- primary_topic = career
- secondary_topics = [family]
- intent_shape = cross_topic_influence
- influence source = mother / family line

错误理解：
- 因为 entry_topic_key=career，就只套事业模板，忽略母亲/家庭线索。
```

### 8.5 人生规划报告建议

不建议把人生规划机械按 7 岁平均切段作为核心算法。

产品展示可以按人生阶段组织，但占星主轴应来自 Domain：

- 法达大限 / 子限：人生章节与当前谁管事。
- 次限月亮：情绪季节与内在阶段。
- 日返 / 月返：年度和月度快照。
- 行运窗口：机会、压力、触发点。

0-100 岁可以作为报告展示范围，不作为算法上限，也不应该一次性预展开存储。

## 10. 报告产品分层

### 10.1 三类报告

| 类型 | 定位 | 适合阶段 |
|---|---|---|
| 小报告 | 单点问题、低门槛、快速生成 | MVP 可做 |
| 标准报告 | 完整主题、主力付费产品 | 需要 Report Compiler |
| 深度报告 | 高价值长周期、多章节、可持续追问 | 后置，不提前商业化 |

### 10.2 小报告

适合问题：

- 最近事业卡在哪里？
- 这段关系怎么看？
- 我最近为什么情绪反复？
- 我适合怎样学习？

价值：快速、便宜、结构化、可保存、可继续聊。

### 10.3 标准报告

适合主题：

- 情感。
- 事业。
- 财富。
- 学业。
- 自我。
- 家庭 / 亲子。

需要能力：主题章节、证据链、结论摘要、待验证点、继续追问。

### 10.4 深度报告

适合主题：

- 年运。
- 人生走向。
- 0-100 岁人生规划。

需要能力：Report Compiler、时间线、章节版本化、长期复盘、可追问上下文。

当前阶段不建议提前售卖高价深度报告。

## 11. 免费体验与付费平衡

免费 Chat 应该足够好，不能被故意削弱。

付费报告的价值不在于“免费不给你答案”，而在于：

- 帮用户把多轮 Chat 整理成结构化资产。
- 把 Domain 证据链、时间线、章节和待验证点组织起来。
- 能保存、复盘、更新、继续深聊。
- 对重要主题提供更稳定、更完整的交付形态。

推荐路径：

```text
首页陪伴 → 免费 Chat 建立信任 → 点亮 / 记忆 / 来信 → 用户形成具体问题 → 主题观星台 → 小报告 / 标准报告 → 拿报告继续 Chat
```

## 14. 验收标准

### 14.1 页面职责验收

- 首页看起来像花园，不像 dashboard。
- Chat 能看到点亮、记忆、来信、行动、验证的闭环。
- 信箱像记忆资产空间，不像消息列表。
- 宇宙清楚区分自我星盘轮、主题观星台、沉淀判断。
- 我的页不出现预测货架。

### 14.2 数据闭环验收

完整路径必须成立：

```text
首页 → mood check / 和它聊聊 → Chat → 点亮 / 记忆 / 来信 → 信箱 → 宇宙 → 我的
```

### 14.3 Domain 硬线验收

- 没有前端硬编码预测结论。
- 没有第二套路由命名回潮。
- 主题观星台只展示入口和证据链状态。
- 报告入口不绕过后端 Conclusion / Finding / Report 字段。
- 用户可见占星结论必须来自 evidence chain，包含宫位、承载者、状态、连接、时间层。
- 不展示“净分 / 净吉凶”；`TimelineWindow.net_score`、`raw_score`、`dignity_score` 只可作为内部排序 / 兼容 / 审计。
- 年度小限只能作为 `annual_activation` 辅助层，不能和法达并列抢时机权威。
- 行运只能作为 trigger，不能单独断事。
- LLM 和前端都不能决定吉凶、权重、征象星或时机权威。

### 14.4 工程验收

- `npm run type-check`
- `npm run build:h5`
- `git diff --check`
